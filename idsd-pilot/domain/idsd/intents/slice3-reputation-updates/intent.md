# 意图：切片 3 —— 信誉更新机制与异常检测

## 目标

让域内的跨群协作跑通"发起 → 自动路由 → 执行 → 信誉回流"的闭环，并引入协作评分与异常检测：接收方可以对协作结果评分（复用群层评审语义），连续低分（评审拒绝）的群在能力发现中被标记降级。**全部机制复用群层现有原语，不新增规则族**（规则预算保持 ≤ 1：唯一的域层规则仍是信誉聚合）。

## 约束

- **域协作发起（自动路由）**：`POST /api/domains/:id/tasks`——成员群声明 `required_capabilities`，域按能力发现（`required ⊆ 声明能力`）选出匹配群，**排除发起群自身**，取域级信誉最高者（同分按 joined_at 升序）；在目标群内创建群任务（复用 group_tasks 机制，域层内部直插，不经过群任务发布 API 的成员校验——发起团队并非目标群成员）。无匹配群 → 400。
- **任务索引**：新增 `domain_tasks` 表（task_id / domain_id / requester_group_id / target_group_id / created_at），记录域协作任务归属（总体意图允许域持有"任务索引"）。schema v10 → v11，PRAGMA user_version = 11，不破坏现有数据。
- **执行与信誉回流（零新规则）**：目标群的成员团队通过现有 `group-claim` 认领 → 授权批准（复用授权闸门）→ 完成/失败时群层 `recordTaskReputation` 自动记录执行团队信誉 → 切片 2 的域级信誉聚合实时反映。**协作结果即时反映到信誉，天然满足"5 分钟内"期望。**
- **协作评分（复用评审语义）**：`POST /api/domains/:id/tasks/:tid/rating`——仅发起群可评分（403）；任务必须已完成（400）；每个任务只能评分一次（400）；`approved` → review_approved（+1）、`rejected` → review_rejected（-2），记在执行团队于目标群的信誉上。薄封装，不引入 1-5 星等新原语。
- **异常检测（信誉原语 + 标记字段）**：对成员群 G，取其团队在域内成员群中的评审事件（review_approved/review_rejected），按时间倒序数**连续 rejected 次数**，≥ 5（常量 `MAX_CONSECUTIVE_REJECTIONS`）→ discover / reputation 结果中 `flagged: true`（能力被标记）；approved 打断连续计数。实时计算，不加新表。
- **agent 团队归属写入路径**：现有 `PATCH /api/agents/:id` 扩展支持 `team_id` 字段（agents.team_id 是既有列，但无 HTTP 写入路径，现有测试靠手工 UPDATE 绕过）——这是既有数据模型的补全，不算新规则。
- **访问控制**：发起/评分/查询仅限域成员（非成员 403）；域不存在 404；缺参 400。
- **向后兼容**：不新增 npm 依赖；不启用域功能时团队/群行为完全不变。
- **本切片不做**：跨域任务（切片 4）、能力标签自动降级（仅标记，不删除声明）、市场机制。

## 失败条件

- 路由到能力不匹配的群（required ⊄ 声明能力）。
- 路由到发起群自身（自刷协作）。
- 非发起群能对协作任务评分。
- 未完成的任务可被评分，或同一任务可重复评分。
- 连续 5 次评审拒绝后，该群在发现结果中未被标记。
- 域层读取群内数据（消息、Agent 通信、内部任务日志）才能工作。
- 新增规则族（除信誉聚合外）或新增 npm 依赖。
- 任何现有团队/群测试失败。
