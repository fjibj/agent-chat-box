# IDSD 开发"域"层实战总结

> 本文档基于 2026-08-02 ~ 2026-08-05 用 IDSD 方法完整开发 agent-chat-box 域层的实战记录。
> 配套文档：《用IDSD开发_域_层的实操指南.md》（方法论）、《idsd-pilot/domain/PROJECT_PROFILE.md》（域层画像）、
> `idsd-pilot/domain/idsd/intents/domain-overall/intent.md`（总体意图）、`checkpoint.md`（逐切片战报）。
>
> **核心结论先行**：域层 5 个切片全部由 AI 代理盲考构建、考官独立判分闭环通过——
> 16/16 → 24/24 → 34/34 → 39/39 → 40/40 自动场景 + 26 项人工验收。
> "域层能不能全交给 AI"的答案是：**能，前提是 Intent 够锐、holdout 够硬、考官必须独立。**

## 一、实战流水线总览

```
总体 Intent（一次，用户拍板）
        │
        ▼
┌──────────────────────────────────────────────┐
│  切片循环（每个切片重复）                        │
│                                              │
│  ① 调研现状 → ② 切片 Intent → ③ Expectations   │
│  → ④ holdout 场景 → ⑤ 自查 → ⑥ 派构建代理       │
│  → ⑦ 评估判分 → ⑧ checkpoint/status/commit     │
└──────────────────────────────────────────────┘
        │
        ▼
切片 0：评估自动化（一次性投资，先于一切切片）
```

**切片顺序（实操指南推荐，实际完全沿用）**：

| 切片 | 内容 | 盲考结果 |
|---|---|---|
| 0 | holdout 评估自动化（evaluate.ts v2） | 5/5 自检 |
| 1 | 域数据模型 + 注册 API（schema v9→v10） | 16/16 |
| 2 | 能力发现 + 信誉查询（只读） | 24/24 |
| 3 | 信誉更新 + 异常检测（schema v11） | 34/34 |
| 4 | 多域交互边界 + 信誉隔离（schema v12） | 39/39 |
| 5 | 域层 UI（DomainsPage，纯前端） | 40/40 + MANUAL 26 项 |

## 二、完整步骤

### 切片 0（先做，且只做一次）：评估自动化

**这是整个流程最重要的投资**，先于任何功能切片。

- 写 `evaluate.ts`（v2 评估器）：基于 Fastify `app.inject` 进程内执行 HTTP 断言，不起服务、不占端口。
- **每场景独立全新数据库**（DATA_DIR 指向临时目录，逐场景重建），场景之间零污染。
- 场景文件带 JSON front-matter 声明断言：`method/url/body/expect/capture` + 匹配操作符
  （`$exists/$eq/$ne/$gt/$gte/$lt/$lte/$startsWith/$endsWith/$contains/$matches/$length/$any/$all/$none`）+ `{{var}}` 捕获替换。
- 无断言场景自动标 **MANUAL**（人工验收），不参与通过率。
- **自动发现 API 模块**：扫描 `packages/server/src/api/` 下所有 `register*Routes` 并注册——
  后续切片新增 API 时评估器零改动。
- 基线门禁（`npm test` + typecheck）可 `--skip-baseline` 跳过。

**教训**：切片 0 看似"不产出业务价值"，但它把后续 5 个切片的判分成本从"每次人工回归"降为"一条命令"。
没有它，盲考闭环无法规模化。

### 切片循环的 8 步

**① 调研现状（出题人的功课）**
- 精读：实操指南对应切片定义 → 总体意图（约束/失败条件）→ 相关现有代码（被复用机制的确切行为）。
- 例：切片 3 前读透了群层 `reputation.ts`、`task-queue.ts`、`group-tasks.ts`、`reviews.ts`，
  才发现 `PATCH /api/agents/:id` 缺 `team_id` 写入路径（既有列无 HTTP 口）——补成切片 3 附带项。
- 调研不到位，Intent 就会臆造，场景就会失真。

**② 起草切片 Intent（用户拍板）**
- 结构：目标（一两句）+ 约束（可验证的质量属性）+ 失败条件（二进制底线）。
- **约束从总体意图推导**，不新造：切片 3 的"自动路由取信誉最高"、"评分仅发起群"、
  "连续 5 次 rejected 标记"全部从总体意图"规则预算 ≤ 1 / 单群不可操纵信誉"推出。
- 我代为拍板的点（如成员机制同构、不做市场机制）要**显式标注**，用户隐含认可也要记录。
- **规则预算检查**：本切片是否新增了规则族？域层全程只新增"信誉聚合"一条规则，其余全部复用群层原语。

**③ Expectations（用户语言）**
- 成功 / 失败 / 边界三张表，每条是"场景 → 期望行为"。
- 语言用业务语言，不用技术语言；它同时是构建代理的验收指南和 holdout 场景的出处。

**④ holdout 场景（考卷）**
- 每个 Expectation 至少对应一个可执行场景；复杂期望拆多 check。
- 成功场景走完整链路（切片 3 的闭环场景含"发起→认领→授权→完成→评分"40+ 个 check）。
- 关键：**场景 setup 全走 HTTP**（建团队/群/域/agent 都用 API），不依赖任何内部状态。
- UI 类切片用 MANUAL 清单（26 项人工验收项），评估器自动标 MANUAL。

**⑤ 自查场景（出题人必须自己先过一遍）**
- 链路能真实走通吗？每步的 API 契约和状态码对吗？断言符合评估器操作符语义吗？
- **这是本流程最大的坑集中地**，见"注意事项"第三节。

**⑥ 派构建代理（盲考）**
- 任务书要素：Goal / 必读文档清单（按顺序）/ **红线** / 实现范围 / 质量门禁 / 回报格式。
- 红线示例：禁止读取 `holdout/`、禁止 git 操作、禁止新增 npm 依赖、（UI 切片加）禁止改后端。
- 代理不可见 holdout，实现只能依据 Intent + Expectations + 自己的代码阅读。
- 每切片一次 `session_spawn`，`runTimeoutSeconds` 按量级给（1800~2400s）。

**⑦ 评估判分（考官独立）**
- 跑全量场景（旧场景回归 + 新场景），结果存档 `results/<version>.json`。
- **失败分流**：考题问题（断言/状态码/场景设计错）→ 修考卷重跑；实现缺陷 → 发回构建代理修复。
- 判别标准：看失败详情是断言与实现语义不符，还是实现行为本身违反意图。
- 修复实现缺陷时，通过 `session_send`（follow_up）下发缺陷说明 + 修复方案，红线不变，不可透露考卷。

**⑧ 收尾（checkpoint / status / commit）**
- `checkpoint.md` 追加本切片段：目标、评估结果、关键设计点、交付物、质量门禁、遗留。
- `idsd-status.yaml` 加 build/evaluation 两个 phase + `version_tags`（记录每次评估版本）。
- **git commit 必须由考官做**（构建代理红线禁 git，成果悬置期间随时可能丢）——每个切片闭环后立即提交推送。

## 三、注意事项与踩坑清单（按重要性排序）

### A. 出题质量（最高优先）

1. **状态码别臆测，先查实现约定**。切片 3 的 7 个场景全挂在断言 `200` 而实现返回 `201`
   （REST 创建惯例）——考题问题，实现零缺陷。出题前先确认"这个端点按现有代码惯例该返回什么"。
2. **匹配操作符语义要对上**。`$contains` 只支持字符串，数组要用 `$any: {$eq}`（切片 5 踩过）。
   操作符清单在 evaluate.ts 头部注释里，出题前读一遍。
3. **场景只测本切片的数据面**。切片 5 我多加了一个"认领" check——它属于群层操作，
   不在 DomainsPage 数据面内，还臆测了 400（实现返回 404 更合理）。删掉后场景回归纯粹。
4. **自查不是可选项**。5 个切片里 4 次评估插曲都是考题自身问题（200/201、漏参数、
   $contains、多余 check），没有一个来自实现。出题人自查到位，一轮过的概率大幅上升。

### B. 评估器与场景文件

5. **批量改场景文件禁用 PowerShell 写回**（`Set-Content` 引入 UTF-8 BOM + CRLF），
   BOM/CRLF 会破坏 `front-matter` 正则解析 → 场景被误判 MANUAL。用 write 工具改写，保持 LF。
   这是切片 3 的真实事故（v2/v3 连续两轮 7 个场景误判 MANUAL）。
6. **版本号递增**：每次评估用新 version 标签（slice3-v1~v4），失败轮次的结果也存档——
   它是"考题问题 vs 实现缺陷"判别的证据链。

### C. 构建代理管理

7. **红线要可验证、可执行**：holdout 不可读 / 无 git / 无新依赖，三条每次都写。
   实现代码放在哪、测试怎么写，代理自己决定——考的就是这个。
8. **轮次上限会打断交卷**：切片 3、4 的构建代理都在 60 轮上限被终止，但交卷内容完整。
   收到 error 状态先看交付物是否齐全、质量门禁是否跑完，**别急着重派**；缺的收尾动作（如
   prettier 检查）考官自己补跑即可，不必浪费一次 spawn。
9. **交卷声明的质量门禁要复核**：代理说全绿，考官评估时顺带抽查（切片 5 我补跑了 web vitest
   与 quality:gates）。盲考的价值在于"实现不可见考卷"，不在于"相信代理自报"。
10. **任务书要写"必读文档清单"**：PROJECT_PROFILE → 总体意图 → 本切片 Intent/Expectations →
    参照实现文件。顺序即依赖顺序，代理照读就能拿到全部上下文，不靠猜。

### D. 质量门禁

11. **区分存量偏差与新增缺陷**：prettier 报 3 个文件是提交基线就存在的（stash 回基线验证过），
    不是构建代理引入。判断方法：`git stash` 后在基线跑同一检查对比。
12. **测试分层明确**：构建代理的单元/组件测试是自证（不算 holdout）；holdout 场景才是判分。
    两者都绿才算闭环。

### E. 流程纪律

13. **commit 及时，考官代劳**：构建代理禁 git，成果在代理交卷到考官提交之间是"悬置态"——
    每切片闭环后立即提交推送，别攒。
14. **产品决策权在用户**："什么是对的"由用户定义。Intent/Expectations 我起草、用户拍板；
    代为拍板的点显式标注并记录用户隐含认可。用户的"可以，继续"是放行信号，不是免责声明。
15. **规则预算 ≤ 1（分形递归）**：每切片设计自问"是否新增规则族"。
    域层兑现方式：协作执行复用群层 `group_tasks`/`recordTaskReputation`，评分薄封装映射
    review 事件，异常检测=连续 rejected 计数+标记字段，不加表不加原语。

### F. 设计与实现的隐藏陷阱

16. **隔离语义最容易漏**：切片 4 第一次由 holdout 抓出真实实现缺陷——`reputation_records`
    无域归属，群 B 在域 A 的评分污染其在域 B 的信誉（v1 38/39 唯一失败）。
    修复：schema v12 加可空 `domain_id`（NULL=群层事件计入所有域；非 NULL=域事件只计入所属域），
    域协作全生命周期事件打域标记，聚合与连续计数按域过滤。
    **教训**：聚合语义的边界条件是实现最容易忽略的角落，holdout 必须专门出隔离场景。
17. **"同团队不能认领"是硬约束**：手工验证协作闭环时，执行群必须属于不同团队——
    否则 group-claim 会被拒，链路卡死（真实踩过，靠建第二个团队解决）。
18. **UI 数据面场景与真实操作路径对齐**：域列表只显示"自己参与的域"，非成员群在 UI 上
    看不到域——"非成员 403"在 UI 层是不可达路径，验证方式是"隔离正确 + 后端 403 正确"，
    而不是"UI 弹出 403 提示"。

## 四、角色与机制（这套流程为什么成立）

| 角色 | 是谁 | 职责 | 关键原则 |
|---|---|---|---|
| 产品所有者 | 用户 | 定义"什么是对的"：拍板 Intent/Expectations、人工验收 MANUAL 项 | 只定义目标，不规定实现 |
| 出题人/考官 | Cola | 调研现状、起草 Intent、写 holdout 场景、判分、修考卷、提交 | **独立于构建代理**，考卷对代理不可见 |
| 构建代理 | 子会话（worker） | 依 Intent+Expectations 自主实现，跑自证门禁 | 红线约束内自由；不可见考卷 |
| 评估器 | evaluate.ts | 进程内执行 HTTP 断言，逐场景独立库 | 自动发现 API 模块，零维护 |

**盲考闭环的三个支柱**：
1. **考卷隔离**——代理看不到 holdout，杜绝"应试式优化"。
2. **独立判分**——考官用另一套断言判分，不信任代理自报。
3. **考题纠错机制**——考题自身错了要能识别（区分考题问题 vs 实现缺陷），否则会冤枉实现。

## 五、验证数据与缺陷统计

| 切片 | 自动场景 | MANUAL | 评估轮次 | 失败性质 |
|---|---|---|---|---|
| 1 | 16/16 | - | v1(全挂：评估器未注册新路由), v2 | 考题/工具问题 |
| 2 | 24/24 | - | v1(23/24：考题漏传 group_id), v2 | 考题问题 |
| 3 | 34/34 | - | v1(27/34：断言 200 vs 实现 201), v2/v3(CRLF/BOM 误判), v4 | 考题问题 ×2 + 工具问题 |
| 4 | 39/39 | - | v1(38/39：**实现缺陷**——信誉不隔离), v2 | **实现缺陷** |
| 5 | 40/40 | 26 项全绿 | v1(39/40：$contains 数组 + 多余 check), v2, v3 | 考题问题 ×2 |

**结论**：
- 5 个切片、12 轮评估，**实现缺陷只有 1 个**（切片 4 信誉隔离），且被 holdout 精确抓住并修复。
- 其余 8 次失败全是出题/工具问题——说明**实现质量整体过硬，出题质量是主要瓶颈**。
- 切片 4 证明：考官独立判分不是仪式，它抓得住真实缺陷。
