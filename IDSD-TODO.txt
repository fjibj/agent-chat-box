核心要点（来自 ima 笔记）

IDSD 与 BMAD 的本质区别：不是"有没有设计"，而是"设计的所有权归谁"

┌──────────────┬────────────────────────────┬────────────────────────────────────┐
│     维度     │         BMAD (SDD)         │                IDSD                │
├──────────────┼────────────────────────────┼────────────────────────────────────┤
│ 谁定义"对"   │ 规格文档，人与 AI 共创协商 │ 意图 + 期望，只由想要结果的人写    │
├──────────────┼────────────────────────────┼────────────────────────────────────┤
│ 完成由谁判定 │ 规格验收标准 + 人工审查    │ Holdout Set 场景边界（代理看不到） │
├──────────────┼────────────────────────────┼────────────────────────────────────┤
│ AI 角色      │ 多智能体模拟敏捷团队       │ 在明确边界内自主构建               │
├──────────────┼────────────────────────────┼────────────────────────────────────┤
│ 最大风险     │ 环节间上下文丢失/幻觉      │ 代理在规格留白处自行填补           │
└──────────────┴────────────────────────────┴────────────────────────────────────┘

关键结论：
1. IDSD 不是不要设计，而是把设计"内化"到代理构建循环中——人定义"什么是对的"，代理决定"怎么实现"。
2. Expectations 不追求覆盖所有场景，而是通过 Holdout Set 机制防止代理"应试"。
3. 适合 IDSD 的前提：产品是你主导、你能用用户语言精确描述边界、信任 harness 管理 Context。
4. 最务实路径是混合路线：小功能走 IDSD Fast/Planned，战略级架构仍保留 BMAD 人工审查。
